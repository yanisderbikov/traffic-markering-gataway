# traffic-markering-gataway

Входная точка проекта: один публичный адрес, за которым живут бэкенд и фронтенд.
Это nginx, который по префиксу пути решает, куда отправить запрос:

| Путь | Куда |
|---|---|
| `/api/**` | бэкенд (`BACKEND_URL`) |
| `/v3/api-docs`, `/swagger-ui/**` | бэкенд — Swagger и схема для генерации клиента |
| `/healthz` | сам гейтвей, отвечает `200 ok` |
| всё остальное | фронтенд (`FRONTEND_URL`) |

Адреса бэка и фронта задаются переменными окружения при старте контейнера,
образ пересобирать не нужно.

Соседние репозитории:
`/Users/user/IdeaProjects/traffic-markering-back`,
`/Users/user/IdeaProjects/traffic-markering-front`.

## Переменные окружения

| Переменная | Обязательна | Пример | Зачем |
|---|---|---|---|
| `BACKEND_URL` | да | `http://traffic-markering-back:8090` | куда проксировать `/api/**` |
| `FRONTEND_URL` | да | `http://traffic-markering-front:80` | куда проксировать остальное |
| `PORT` | нет, по умолчанию `80` | `8080` | порт гейтвея внутри контейнера |
| `CACHE_TTL` | нет, по умолчанию `10m` | `5m` | сколько живёт закешированный ответ |

Схему можно не писать — подставится `http://`. Слэш на конце адреса срезается.
Без `BACKEND_URL` или `FRONTEND_URL` контейнер не стартует и пишет, чего не хватает.

Адреса могут быть как именами сервисов в docker-сети, так и публичными
`https://`-адресами: для них включён SNI, а заголовок `Host` уходит апстриму его
собственный, так что хостинги вроде Railway маршрутизируют запрос правильно.
Исходный хост и схема клиента передаются в `X-Forwarded-Host` и
`X-Forwarded-Proto` (если гейтвей сам стоит за TLS-терминатором, берётся его
`X-Forwarded-Proto`).

Образец — в `.env.example`. Реальный `.env` в `.gitignore`.

## Кеш

Одинаковые запросы гейтвей отдаёт из своего кеша, не трогая бек и фронт.
Ответ живёт не дольше `CACHE_TTL` (по умолчанию 10 минут), после этого
следующий запрос снова уходит апстриму. Пока один запрос ждёт апстрим,
такие же параллельные запросы ждут его результат, а не идут апстриму сами.

Что попадает в кеш:

- только `GET` и `HEAD` с ответом `200`, `301` или `302`;
- только запросы **без** заголовка `Authorization` — всё, что ходит с JWT,
  всегда идёт на бек и в кеш не пишется, чтобы данные одного пользователя
  не уехали другому;
- ключ кеша — путь вместе с query-строкой, так что `?page=2` кешируется
  отдельно.

Мимо кеша всегда: `/api/auth/**`, `/api/social/callback/**`, `/api/tech/**`,
`/api/actuator/**`, `/healthz`.

`Cache-Control` и `Expires` от апстримов игнорируются: Spring Security по
умолчанию ставит `no-store` на всё, а nginx фронта — год на `/assets/`,
и то и другое перекрывается общим `CACHE_TTL`. Из этого следует, что после
деплоя фронта или смены публичных данных на беке старый ответ может отдаваться
ещё до `CACHE_TTL`.

В каждом ответе есть `X-Cache-Status`: `HIT`, `MISS`, `BYPASS` (запрос
намеренно мимо кеша) или `EXPIRED`.

```bash
curl -sI http://localhost:8080/api/public/campaigns | grep X-Cache-Status
```

Кеш лежит в `/var/cache/nginx/gateway` внутри контейнера, до 512 МБ, и
пропадает вместе с контейнером.

## Что поменять в беке и фронте

Через гейтвей фронт и API живут на одном origin, поэтому:

- фронт собирается с `VITE_API_URL`, равным публичному адресу гейтвея
  (или тому же домену, на котором открыт сайт);
- в беке `URL_BACK` — публичный адрес гейтвея: из него собираются redirect URI
  для OAuth соцсетей и server url в Swagger;
- в `ALLOWED_ORIGINS` бека достаточно адреса гейтвея.

## Локальный запуск

```bash
cp .env.example .env
```

Значения по умолчанию в `.env.example` смотрят на хост: бэк из
`docker-compose.yml` бэкенда на `8090` и vite-дев-сервер фронта на `3000`.

```bash
docker compose up --build
```

Гейтвей будет на `http://localhost:8080`. Проверить маршрутизацию:

```bash
curl -i http://localhost:8080/healthz
```

```bash
curl -i http://localhost:8080/api/public/campaigns
```

Порт публикации задан в `docker-compose.yml` (`8080` снаружи, `PORT` внутри).

## Как устроено

- `nginx/gateway.conf.template` — конфиг nginx с плейсхолдерами `${PORT}`,
  `${BACKEND_URL}`, `${FRONTEND_URL}`, `${CACHE_TTL}`.
- `docker-entrypoint.d/25-render-gateway.sh` — запускается стандартным
  entrypoint'ом образа `nginx:alpine` перед стартом: проверяет переменные,
  нормализует адреса и через `envsubst` кладёт готовый конфиг в
  `/etc/nginx/conf.d/default.conf`.
- `Dockerfile` — `nginx:alpine` плюс эти два файла.

Проверить, что конфиг собирается, не поднимая сервис:

```bash
docker build -t traffic-markering-gateway . && docker run --rm -e BACKEND_URL=http://example.com:8090 -e FRONTEND_URL=http://example.org traffic-markering-gateway nginx -t
```

## Деплой

`.github/workflows/deploy.yml` на пуш в `main` собирает образ и пушит в
`ghcr.io/yanisderbikov/traffic-markering-gataway` (теги `latest` и короткий sha).
Переменные окружения задаются на стороне хостинга, в образ ничего не зашито.
Платформы, которые сами выдают `PORT` (Railway и подобные), подхватываются
без настройки.
